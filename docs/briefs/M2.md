# M2: The app contract

**For:** Claude Sonnet, building in Claude Code, in the `~/Developer/falak` worktree on branch `rehaul`.
**Read first:** `CLAUDE.md`, `ARCHITECTURE.md`, then the "Tools are apps" and "Confirmations,

## Goal

Define what an app is, and build everything the core needs to load and run apps:
- manifests
- input validation
- effects, which decide confirmations
- pending asks
- an action log with undo
- per-app settings, secrets and storage

Then build three real apps that prove the contract: **calculator**, **memory** and **camera** (a single
photo).

There's no agent loop yet (that's M3). In this milestone apps are driven from the CLI and tests, so you can
run any action by hand.

- the agent loop, prompts, Claude calls and vision

## 1. Manifest format: `jarvis/apps/<name>/manifest.toml`

```toml
[app]
name = "calculator"            # must equal the folder name
description = "Exact arithmetic and common math functions."   # written for the model; 1-2 sentences
runs_on = "host"               # "host", or "node:<capability>" (e.g. "node:camera")
secrets = []                   # .env keys this app may read; it gets no others

[settings]                     # optional: declared settings and their defaults
precision = 12

[[actions]]
name = "evaluate"              # snake_case, unique within the app
description = "Evaluate an arithmetic expression and return the exact result."
effect = "read"                # read | local | outbound | irreversible
handler = "evaluate"           # function in actions.py; defaults to name
# undo = "unevaluate"          # local actions only: handler that reverses it
# confirm = "Send this to {to}?"  # required for outbound and irreversible: plain question, {arg} fields
# log_args = false             # keep the arguments out of the action log (private content)

[actions.input]                # JSON Schema for the arguments (supported subset below)
type = "object"
required = ["expression"]
additionalProperties = false
[actions.input.properties.expression]
type = "string"
description = "For example '2 * (3 + 4)' or 'sqrt(2)'."
```

**Rules the loader enforces**, each failure raising `ManifestError` with the file and the reason:
- Unknown keys anywhere are an error, the same strictness as settings.
- `name` matches the folder.
- `runs_on` is `host` or `node:<capability>`.
- `effect` is one of the four values.
- `undo` appears only on `local` actions, and its handler exists.
- `confirm` is present on `outbound` and `irreversible` actions, and its `{fields}` are input properties.
- Every handler exists in `actions.py`.
- `input` uses only the supported JSON Schema subset:
  - `type`: object, string, number, integer, boolean or array
  - `properties`, `required`, `additionalProperties`, `enum`, `items`, `description`, `default`
  - `minimum`, `maximum`, `minLength`, `maxLength`

  Any other keyword is an error, so nothing is silently ignored.
- `sessions` and `jobs` are **not** valid yet. M5 and M6 add them.

**`runs_on = "node:<capability>"` in M2:** there's no node yet, so the registry runs these actions in-process,
as if this Mac has every capability. Put that decision in one clearly named place
(`jarvis/core/apps.py`, `run_on_this_machine()`) so M5 can replace it with routing.

## 2. What apps get: `jarvis/core/api.py`

This is the only module apps may import from the core (the layout test enforces it). Keep it small.

```python
@dataclass(frozen=True)
class Result:
    text: str                                  # short, human-readable outcome
    data: dict | None = None                   # structured result for the loop (M3)
    undo: dict | None = None                   # what the app's undo handler needs, if the action has one
    attachments: tuple[Attachment, ...] = ()   # e.g. a photo

@dataclass(frozen=True)
class Attachment:
    kind: str                                  # "image" for now
    path: Path                                 # a private temp file; the core deletes it (see 6)
    mime: str

class ActionError(Exception):
    """A failure to tell Elijah about in plain words ('The camera is in use by another app')."""

class AppContext:                              # passed as the first argument to every handler
    name: str
    settings: Mapping[str, object]             # manifest [settings] defaults overridden by settings.toml [apps.<name>]
    secrets: Mapping[str, str]                 # only the keys the manifest lists
    log: logging.Logger                        # "jarvis.apps.<name>"
    db: sqlite3.Connection                     # see the storage rule below
    def temp_path(self, suffix: str) -> Path   # private temp file (0600 in a 0700 folder)
```

Handler signature: `def evaluate(ctx: AppContext, expression: str) -> Result`. The arguments are the
validated input as keyword arguments. An undo handler is `def x(ctx, undo: dict) -> Result`.

**Storage rule:**
- An app may create and use only tables named `<app>_*`.
- It creates them with its own numbered migrations in `jarvis/apps/<name>/migrations/NNNN_*.sql`.
- The core applies app migrations per app. Add a core migration `0002_apps.sql` with
  `app_migrations(app TEXT, version INTEGER, applied_at TEXT, PRIMARY KEY (app, version))`.
- A contract test checks that app migration files only create, alter or drop `<app>_*` tables.

## 3. The registry: `jarvis/core/apps.py`

- `load_apps(settings, apps_dir=DEFAULT_APPS_DIR) -> Registry`:
  - Finds `*/manifest.toml` under the apps folder.
  - Skips apps with `enabled = false` in `settings.toml` `[apps.<name>]` (default enabled).
  - Validates every manifest and imports each `actions.py` with `importlib` by path or module name. The
    core must never import an app statically.
  - Applies app migrations.
  - `apps_dir` is a parameter so tests can load fixture apps.
- `Registry.actions()`:
  - lists every action as a `ToolSpec(app, action, description, effect, input_schema)`, which M3 turns
    into native tools
  - tool names are `<app>__<action>` (double underscore)
- `settings.toml` `[apps.<name>]` keys must be either `enabled` or a declared setting. Anything else
  raises `SettingsError`, naming the app.

## 4. Validation: `jarvis/core/schema.py`

A small validator for the supported subset (stdlib only, no `jsonschema`).
- `validate(schema, value) -> list[str]` returns readable problems, e.g. `"expression: required"` or
  `"precision: must be ≤ 20"`.
- Fill in `default`s.
- Reject extra properties when `additionalProperties = false`.
- Test it on its own.

## 5. Running actions and the confirmation policy: `jarvis/core/actions.py`

`run(registry, tool_name, args, origin) -> Ran | Asked | Failed`:

1. Look up the action. Validate `args`. Invalid input is `Failed` with the problems; the handler isn't
   called.
2. Decide with `needs_confirmation(effect, origin, allowed) -> bool`. It's a pure function, and the **only**
   place this decision is made:
   - `read` and `local` → run.
   - `irreversible` → always ask.
   - `outbound` → ask, unless `tool_name` is in `allowed` (the learned trust rules; always empty in M2)
     **and** `origin.outside_content` is false.
   - `origin` is `Origin(channel: str, outside_content: bool)`. `outside_content` is true when the turn was
     driven by a web page, email, file or screen text (ARCHITECTURE rule 10).
3. If asking: store an ask and return `Asked(ask_id, question)`.
   - `question` is the manifest's `confirm` template filled from the args.
   - Use a new core table, `asks(id, tool, args_json, question, status, created_at, resolved_at, origin_json)`,
     with `status` one of pending, approved, declined or expired.
4. If running: call the handler with an `AppContext`.
   - `ActionError` → `Failed(message)`.
   - Any other exception → `Failed("Something went wrong in <app>")`, with the traceback logged.
   - Success → `Ran(result)`.
5. **Every** call is logged to a new `action_log` table: id, time, tool, effect, status (ran, failed,
   asked, declined), args (or `"(not logged)"` when `log_args = false`), the result text (≤500 chars) and
   the undo JSON.

Also:
- `answer_ask(registry, ask_id, yes: bool) -> Ran | Failed | Declined`:
  - Runs **exactly** the stored args, and only if the ask is still pending.
  - Asks expire after 24 hours; an expired ask can't be approved.
- `undo(registry, log_id=None) -> Ran | Failed`:
  - Undoes the given entry, or the most recent undoable `ran` entry that hasn't been undone.
  - Calls the app's undo handler with the stored undo data, and marks the entry undone.
  - Undoing twice fails with a plain message.

Put the core tables (`asks`, `action_log`, `app_migrations`) in `0002_apps.sql`.

## 6. Attachments

The core owns cleanup:
- Attachment files live in `<data_dir>/tmp/`, a 0700 folder.
- `run` returns them. The caller (the CLI now, the loop in M3) calls `actions.release(result)` when done,
  which deletes them.
- Anything older than 10 minutes in `tmp/` is deleted on startup.
- Photos are never copied anywhere else, and never logged.

## 7. The three apps

**calculator** (`runs_on = "host"`):
- `evaluate(expression)`, effect `read`.
- A safe evaluator with `ast`. No `eval`.
  - Numbers, `+ - * / // % **`, unary minus and parentheses.
  - Functions: `sqrt sin cos tan asin acos atan log log10 exp abs round floor ceil`.
  - Constants: `pi`, `e`.
- Refuse names, attributes, calls to anything else, and huge powers (exponent > 1000, or a result with
  more than 1,000 digits).
- Results are exact for integers. Floats are shown with `precision` significant digits (a declared setting,
  default 12).
- Errors like division by zero or an unknown function raise `ActionError` with a plain message.

**memory** (`runs_on = "host"`). It owns the facts.
- Its migration `0001_facts.sql`:
  - creates `memory_facts(id, category, key, value, source, updated_at, UNIQUE(category, key))`
  - copies rows from the legacy `facts` table if it exists
  - leaves `facts` itself alone
- Actions:
  - `remember(category, key, value)`, effect `local`. Upserts. The undo data is the previous row, or "it
    didn't exist".
  - `forget(category, key)`, effect `local`. The undo data is the deleted row.
  - `recall(query, category?)`, effect `read`. A case-insensitive substring search over category, key and
    value; up to 20 rows; `data` holds the rows.
- Its undo handler restores the previous state exactly.
- Categories: school, work, money, personal, preference, as an `enum` in the schema.

**camera** (`runs_on = "node:camera"`, so in-process in M2):
- `take_photo()`, effect `read`, `log_args = false`. It returns one image attachment.
- Uses `imagesnap` (installed at `/opt/homebrew/bin/imagesnap`) to write a JPEG into `ctx.temp_path(".jpg")`.
  - Use a declared setting `device` (default `""`, meaning the default camera), passed as `-d` when set.
  - Use a 10-second timeout.
- Plain `ActionError`s for:
  - imagesnap missing
  - camera permission denied (tell him which app needs the permission, the terminal running it)
  - no camera found
  - a timeout
- There's no "only when Elijah asks" rule: senses are ordinary tools (PLAN.md).
- Don't use or touch the old `JARVIS Camera.app` or its folders. The live preview comes back in M5.
- Read `legacy/jarvis/camera.py` for the imagesnap details and error cases, and port behavior, not
  structure.

Each app has `tests/` inside its folder. pytest must collect them: update `testpaths` to include
`jarvis/apps`. App tests use a temp data folder, like M1's fixture. The camera tests mock the subprocess;
don't fire the real camera in tests.

## 8. CLI additions

Keep `cli.py` thin. If it nears 400 lines, split it into `jarvis/cli/` with one module per command group.
- `jarvis apps`: lists apps and their actions, with effect and runs_on.
- `jarvis run <app>.<action> [--args JSON]`:
  - runs as origin `Origin(channel="cli", outside_content=False)`
  - prints the result text, or `Asked #<id>: <question>`, or the failure
  - for attachments, prints kind, size and path, then releases them
- `jarvis asks`: pending asks. `jarvis yes <id>` and `jarvis no <id>` answer one.
- `jarvis undo [<log id>]`.
- `jarvis log [-n 20]`: recent action log entries.

## 9. Tests

- **Contract tests (`tests/test_app_contract.py`)**, run over every real app:
  - the manifest loads
  - every handler exists and its parameters match the schema properties
  - effects and confirm templates are valid
  - `undo` only appears on local actions
  - migrations touch only `<app>_*` tables
  - the app has a `tests/` folder
- **A fixture app** in `tests/fixtures/apps/echo/` with:
  - a `read` action
  - a `local` action with undo
  - an `outbound` action with `confirm = "Send {text} to {to}?"`
  - an `irreversible` action

  Use it to test the whole policy: read and local run; outbound and irreversible ask; approving runs the
  stored args exactly; declining doesn't run; an expired ask can't be approved; the `allowed` set lets
  outbound run only without outside content; irreversible always asks.
- Manifest errors: one small test per rule in section 1.
- Undo: the most recent undoable entry, a given id, a second undo fails, and memory restores exactly.
- Attachments are deleted on release and swept on startup.
- `test_layout.py` still passes. The apps you add must use only `jarvis.core.api`. Files in an app's own
  `tests/` folder may import the core to drive it: make `test_apps_use_only_the_core_api_and_protocol`
  skip them, and add a test showing it still catches a violation in an app's `actions.py`.
